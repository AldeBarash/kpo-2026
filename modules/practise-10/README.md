# Практика 10. Telegram-бот и Kafka: надёжная доставка событий через outbox

## Цель

Доработать AI Gateway из практики 9: после успешного списания кредитов сервис сохраняет событие `CreditsCharged`, доставляет его в Kafka и отправляет пользователю Telegram-уведомление. Через бота пользователь также может узнать свой баланс.

В этой работе нужно освоить разделение приложения на микросервисы, transactional outbox, асинхронную публикацию, повторную доставку, идемпотентного consumer и границы гарантий при межсервисных и внешних HTTP-вызовах.

## Стартовая основа

В эту практику скопированы исходники, миграции, тесты, Dockerfile, Docker Compose и Postman-коллекция практики 9. Биллинг и HTTP API уже реализованы; Telegram, Kafka и outbox предстоит добавить самостоятельно. Каталог `build` не переносится.

Описание исходной предметной области, тарификации и HTTP API находится в [README практики 9](../practise-9/README.md). Все инварианты кошелька, работа резерва и идемпотентность AI-запросов должны сохраниться.

Точки расширения:

- [`BillingService.complete`](src/main/java/studying/gateway/service/BillingService.java) — завершение AI-запроса и окончательное списание в одной транзакции;
- [`UserAccountService`](src/main/java/studying/gateway/service/UserAccountService.java) — операции с пользователем и кошельком;
- [`db.changelog-master.yaml`](src/main/resources/db/changelog/db.changelog-master.yaml) — подключение новых миграций;
- [`application.yaml`](src/main/resources/application.yaml), [`docker-compose.yml`](docker-compose.yml) и [`build.gradle.kts`](build.gradle.kts) — конфигурация и зависимости.

## Обязательная архитектура: два микросервиса

Разделите стартовое приложение на два Gradle-подмодуля с независимыми Spring Boot приложениями:

- `gateway` — исходный HTTP API, пользователи, API-ключи, кошельки, Ollama, одноразовые коды привязки, outbox и publisher в Kafka;
- `telegram-service` — команды бота, привязки Telegram, consumer Kafka, inbox и очередь уведомлений.

У каждого сервиса своя БД, учётная запись, Liquibase changelog, конфигурация и Dockerfile. Можно использовать два PostgreSQL-контейнера или один экземпляр PostgreSQL с двумя БД и отдельными пользователями без доступа к соседней базе. Межсервисные внешние ключи, чтение чужих таблиц и общий DataSource запрещены. В Telegram-сервис не переносите биллинг и зависимости Ollama; Telegram-токен нужен только Telegram-сервису.

```text
Gateway + БД/outbox → Kafka → Telegram-сервис + БД/inbox → Telegram
          ↑                          │
          └──── HTTP: код и баланс ───┘
```

Kafka передаёт `CreditsCharged` из Gateway в Telegram-сервис. Для погашения кода и команды `/balance` Telegram-сервис обращается к защищённому внутреннему HTTP API Gateway. Вызовы между сервисами выполняются вне локальных транзакций и блокировок БД. Общей транзакции двух БД нет: повтор операции должен быть безопасным.

Стартовый проект пока остаётся копией практики 9. Разделение на подмодули и настройка их сборки входят в задание. Реальный платёжный провайдер не нужен.

## Итоговый сценарий

1. Пользователь регистрируется через существующий HTTP API и получает API-ключ.
2. В личном чате с ботом выполняет `/start` и получает инструкцию по привязке.
3. Через защищённый endpoint создаёт одноразовый код привязки и отправляет боту `/link <code>`.
4. Выполняет `/balance`: Telegram-сервис получает через внутренний HTTP API Gateway общий баланс, резерв и доступные кредиты и отправляет их в чат.
5. Пополняет кошелёк учебным endpoint и выполняет запрос к Ollama.
6. Финальная транзакция сохраняет usage, списание и событие в outbox.
7. Фоновый publisher отправляет событие в Kafka.
8. Consumer Telegram-сервиса сохраняет inbox и задание в своей БД, отдельный worker отправляет сообщение в Telegram.

Пример сообщения:

```text
Запрос 974209bd-813a-429b-ae1e-291e732b5a93 завершён.
Модель: qwen2.5:0.5b
Токены: 18 входных, 42 выходных.
Списано: 11 кредитов.
Баланс после операции: 9989 кредитов.
```

Недоступность Kafka или Telegram не должна отменять завершённый AI-запрос или удерживать блокировку кошелька.

## Задание 1. Привязка Telegram и команды бота

Создайте бота через BotFather. Токен передавайте через `TELEGRAM_BOT_TOKEN`; не сохраняйте его в репозитории и не выводите в логи. Для локального запуска достаточно long polling, публичный адрес и webhook не требуются.

Реализуйте команды:

| Команда | Поведение |
| --- | --- |
| `/start`, `/help` | Инструкция по привязке и список команд |
| `/link <code>` | Привязать личный чат к владельцу одноразового кода |
| `/balance` | Вернуть баланс, резерв и доступные кредиты |
| `/unlink` | Отключить привязку и будущие уведомления |

Endpoint Gateway `POST /api/telegram/link-codes` принимает `Authorization: Bearer <API_KEY>` и определяет пользователя по ключу, а не по переданному `userId`. Ответ содержит `code` и `expiresAt`. Код должен быть случайным, одноразовым, действовать не более пяти минут и храниться в БД в виде хеша. Два параллельных `/link` не могут использовать один код для разных операций.

Реализуйте внутренний HTTP API Gateway:

| Метод и путь | Назначение |
| --- | --- |
| `POST /internal/telegram/link-redemptions` | Погасить код и вернуть `userId` |
| `GET /internal/users/{userId}/wallet` | Получить баланс активного пользователя |

Оба endpoint требуют общий сервисный секрет, например `X-Service-Token`, переданный через `INTERNAL_API_TOKEN`. Отсутствующий или неверный секрет возвращает `401`; не храните его в Java-коде и не логируйте. Полный API-ключ пользователя Telegram-сервис не получает и не сохраняет.

Пример тела погашения:

```json
{"updateId":123,"telegramUserId":456,"chatId":456,"code":"одноразовый-код"}
```

В одной транзакции **БД Gateway** погасите код и сохраните результат операции. Повтор с тем же `updateId` и тем же телом возвращает исходный `userId`, включая случай потери первого HTTP-ответа. То же `updateId` с другим телом возвращает `409`; новая операция не может использовать погашенный код. Храните код в квитанции только в виде хеша.

После успешного HTTP-ответа Telegram-сервис в одной транзакции **своей БД** сохраняет привязку, обработанный `update_id` и задание на ответ. Сбой между commit Gateway и commit Telegram-сервиса должен восстанавливаться повторным погашением с прежним ID. Не пытайтесь объединить две БД одной `@Transactional`. При временной недоступности Gateway не отмечайте update обработанным: повторите его позже.

Для `/balance` найдите пользователя по локальной привязке и запросите кошелёк через HTTP. Перед сохранением ответа убедитесь, что привязка не изменилась во время вызова. `/unlink` изменяет только локальную привязку Telegram-сервиса.

Храните `telegram_user_id` и `chat_id` как `BIGINT`/`Long`. Разрешите привязку только из личного чата; username не является идентификатором владельца. Для этой работы один пользователь связан максимум с одним Telegram-аккаунтом, и наоборот. Повторная привязка чужого аккаунта должна завершаться понятной ошибкой, а не перехватывать существующую связь.

Непривязанный пользователь не может получить чужой баланс. Не просите отправлять API-ключ в Telegram. Для `/unlink` проверяйте существующую связь по отправителю и чату. Учтите повторную обработку одного `update_id`: она не должна повторно менять состояние.

## Задание 2. Событие и transactional outbox

Добавьте таблицу `outbox_events` в БД Gateway. Минимальные поля:

```text
id                UUID, PK — это же eventId
aggregate_id      UUID, NOT NULL — userId, ключ Kafka
aggregate_type    VARCHAR, NOT NULL
event_type        VARCHAR, NOT NULL
schema_version    INTEGER, NOT NULL
payload           JSONB, NOT NULL
status            VARCHAR, NOT NULL — NEW, PROCESSING, SENT, FAILED
attempts          INTEGER, NOT NULL
next_attempt_at   TIMESTAMPTZ, NOT NULL
locked_until      TIMESTAMPTZ
lock_token        UUID
created_at        TIMESTAMPTZ, NOT NULL
sent_at           TIMESTAMPTZ
last_error        TEXT
```

Схему можно расширить или обосновать другой набор состояний. Нужны индекс для выборки готовых событий и уникальное ограничение для пары «тип события — AI-запрос», чтобы одно списание не породило несколько логических `CreditsCharged`. Для этого добавьте отдельный `ai_request_id` или другой явный business key.

Пример сообщения в топике `billing.credits-charged.v1`:

```json
{
  "eventId": "35bb8c3e-64e4-46b8-999a-fb8e773118c4",
  "eventType": "CreditsCharged",
  "schemaVersion": 1,
  "occurredAt": "2026-11-14T10:00:00Z",
  "userId": "1a39322c-1b5a-4ef1-8e49-dd37c4e730e5",
  "requestId": "974209bd-813a-429b-ae1e-291e732b5a93",
  "model": "qwen2.5:0.5b",
  "promptTokens": 18,
  "completionTokens": 42,
  "chargedCredits": 11,
  "balanceAfter": 9989
}
```

Payload — снимок данных на момент списания. Повторная отправка сохраняет исходные `eventId`, `occurredAt` и payload. Не включайте API-ключ, prompt, ответ модели или Telegram-токен.

Внутри **одной транзакции PostgreSQL** выполните:

```text
сохранить usage и статус COMPLETED
списать кредиты и записать операции кошелька
создать NEW outbox-событие
commit
```

При rollback не остаётся ни списания, ни события. Повтор HTTP-запроса с тем же `Idempotency-Key` возвращает прежний результат и не создаёт новое событие. Ошибка Ollama и освобождение резерва не создают `CreditsCharged`.

Прямой вызов Kafka из `complete`, отправка только через `AFTER_COMMIT` listener или помещение события только в память не заменяют outbox: процесс может завершиться между commit и отправкой.

## Задание 3. Publisher в Kafka

В Gateway реализуйте фоновую обработку outbox:

1. В короткой транзакции заберите ограниченную пачку готовых записей. Для нескольких worker используйте, например, `FOR UPDATE SKIP LOCKED` и lease с `locked_until` и уникальным `lock_token`.
2. Завершите транзакцию захвата, затем отправьте события в Kafka вне блокировок БД. Ключ сообщения — строковое представление `userId`.
3. Дождитесь подтверждения broker. Только после успеха отдельной транзакцией отметьте событие `SENT` и заполните `sent_at`.
4. При ошибке увеличьте `attempts`, сохраните безопасное описание ошибки и запланируйте retry с увеличивающейся задержкой и верхней границей.
5. После лимита попыток переведите событие в `FAILED`. Предусмотрите описанный в README способ ручного повторного запуска без изменения `eventId`.

Зависшие `PROCESSING` должны снова становиться доступными после истечения lease. Обновление результата выполняется только владельцем актуального `lock_token`, чтобы старый worker не перезаписал состояние нового. Задайте таймаут публикации и согласуйте его с длительностью lease.

Сбой после подтверждения Kafka, но до отметки `SENT` приводит к повторной отправке. Это ожидаемая **at-least-once** доставка. Идемпотентный producer полезен, но не устраняет это окно между Kafka и PostgreSQL.

Одинаковый ключ направляет события пользователя в одну partition, но несколько publisher могут отправить их не по порядку создания. В обязательной части каждое сообщение показывает баланс **после конкретной операции**, consumer не восстанавливает текущий баланс из потока. Строгое упорядочивание по пользователю — дополнительное задание.

## Задание 4. Consumer и уведомления

Consumer группы `telegram-notifications` работает в Telegram-сервисе и читает `billing.credits-charged.v1`. В транзакции своей БД он:

- регистрирует `eventId` в inbox с уникальностью `(consumer_name, event_id)`;
- создаёт задание в `telegram_notifications`, если у пользователя есть активная привязка;
- фиксирует пропуск уведомления, если привязки нет.

Повтор события не создаёт второе задание. Разрешайте подтверждение Kafka offset только после commit этой транзакции. Падение после commit, но до подтверждения offset должно быть безопасно благодаря inbox. Не выполняйте Telegram HTTP-вызов внутри этой транзакции.

Таблица уведомлений содержит как минимум `id`, уникальный `event_id`, `user_id`, `chat_id`, payload сообщения, статус, число попыток, время следующей попытки и время успешной отправки. Для нескольких worker используйте безопасный захват и восстановление зависших заданий, как у publisher.

Отдельный worker отправляет уведомления. Перед отправкой проверяйте актуальность привязки: после `/unlink` или смены чата старые ожидающие задания нужно пропускать. Временные сетевые ошибки повторяются с задержкой; ограничение частоты учитывает `retry_after`; постоянные ошибки, например блокировка бота, не повторяются бесконечно. Неверный JSON или неподдерживаемая версия события не должны навсегда блокировать partition: предусмотрите ограниченные повторы и DLT, например `billing.credits-charged.dlt`. Подтверждайте исходное сообщение только после успешной записи в DLT.

**Граница гарантий:** inbox устраняет повторные задания при повторной доставке из Kafka. Но если Telegram принял сообщение, а worker упал до сохранения результата, retry может отправить его ещё раз. Не заявляйте exactly-once доставку в Telegram. Опишите это окно в README решения; включайте `requestId` в текст, чтобы повтор можно было распознать.

## Задание 5. Миграции и конфигурация

Добавьте атомарные Liquibase-миграции: отдельные файлы для новых таблиц, индексов и ограничений. У каждого сервиса свой master changelog. Старые применённые миграции практики 9 не редактируйте. Связи внутри сервиса и ограничения должны защищаться БД; в Gateway `ddl-auto` остаётся `validate`. UUID пользователя в БД Telegram-сервиса — внешний идентификатор, а не FK в чужую БД.

В Gateway потребуются таблицы одноразовых кодов, квитанций их погашения и outbox; исходные таблицы биллинга остаются здесь. В Telegram-сервисе — привязки, inbox, задания на уведомления и учёт обработанных updates. Выбор структуры обоснуйте. При использовании новых БД опишите создание чистого стенда; перенос существующих данных необязателен, но старую БД не удаляйте автоматически.

Добавьте необходимые зависимости для Kafka и выбранного Telegram-клиента, согласованные с версиями проекта. Конфигурация должна поддерживать:

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_BOT_ENABLED
SPRING_KAFKA_BOOTSTRAP_SERVERS
INTERNAL_API_TOKEN
GATEWAY_BASE_URL
```

Имена параметров batch size, poll interval, lease, числа попыток и задержек retry выберите сами и задокументируйте. При выключенном боте Telegram-сервис должен запускаться без Telegram-токена. Оба сервиса читают настройки только своей БД; `GATEWAY_BASE_URL` нужен Telegram-сервису для внутреннего HTTP API.

Переделайте Docker Compose для запуска `gateway`, `telegram-service`, двух изолированных БД и Ollama. Добавьте broker Kafka в режиме KRaft без ZooKeeper, проверкой готовности и созданием топиков. Зафиксируйте версию образа. Разделите адрес broker для приложения внутри Docker и для инструментов на хосте. Исходный Compose пока поднимает только приложение, PostgreSQL и Ollama — Kafka добавляется в рамках задания.

Остановка Kafka после запуска не должна нарушать HTTP-биллинг: события накапливаются в outbox и отправляются после восстановления broker. Для локального стенда достаточно одного broker; это не демонстрация отказоустойчивого Kafka-кластера.

## Что проверить тестами

В интеграционных тестах запускайте два приложения с разными портами, отдельными БД PostgreSQL и изолированным Kafka broker, например через Testcontainers. Межсервисный контракт проверяйте настоящими HTTP-запросами, а не прямым вызовом сервиса соседнего приложения. Telegram и Ollama в автоматических сценариях замените управляемыми HTTP-заглушками; тесты не должны отправлять сообщения реальным пользователям.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Изоляция сервисов | У Gateway нет таблиц привязок/inbox, у Telegram-сервиса нет кошельков/outbox; доступ к соседней БД не нужен |
| Нет или неверен сервисный секрет | Внутренний API возвращает `401` |
| Gateway погасил код, Telegram-сервис упал до commit | Повтор с прежним ID восстанавливает привязку без повторного использования кода |
| Одинаковый ID погашения с другим телом | Gateway возвращает `409` |
| Gateway временно недоступен при `/link` или `/balance` | Update не теряется и повторяется после восстановления |
| `/balance` при раздельных БД | Ответ получен через HTTP Gateway |
| Успешное списание | Usage, журнал и ровно одно outbox-событие зафиксированы вместе |
| Исключение после сохранения outbox до commit | Ни списание, ни событие не сохранены |
| Повтор `Idempotency-Key` | Второго списания и второго события нет |
| Ошибка Ollama | Резерв освобождён, `CreditsCharged` отсутствует |
| Kafka недоступна | HTTP-запрос успешен, событие остаётся для retry |
| Kafka восстановилась | Событие доставлено и помечено `SENT` после подтверждения |
| Сбой после Kafka ack до `SENT` | Повтор сохраняет `eventId`, consumer создаёт одно задание |
| Два publisher и истёкший lease | Захват безопасен, старый worker не изменяет чужую запись |
| Повтор сообщения после commit inbox | Второе задание не создаётся |
| Telegram временно недоступен | Уведомление повторяется, биллинг не меняется |
| Бот заблокирован или привязка удалена | Нет бесконечных попыток или отправки в старый чат |
| Просроченный, использованный или одновременно погашаемый код | Нельзя получить чужую привязку или использовать код дважды |
| Повтор `update_id` | Нет повторного изменения состояния |
| Некорректное событие | Ограниченные повторы и DLT; следующие события обрабатываются |

Проверяйте асинхронные результаты с ограниченным ожиданием условия, а не фиксированным долгим `sleep`. Отдельно продемонстрируйте окно возможного повторного сообщения Telegram после внешнего успеха и до записи в БД.

## Что сдавать и показать на защите

- Два независимых приложения `gateway` и `telegram-service`, их миграции и Dockerfile, общий Compose с изолированными БД и Kafka, пример конфигурации без секретов.
- Автоматические тесты на транзакционность, повторы и восстановление после сбоев.
- README решения: архитектура, команды запуска, настройки retry и точные границы гарантий.
- Демонстрацию: привязка → `/balance` → AI-запрос → outbox → Kafka → сообщение в Telegram.
- Демонстрацию сбоя: остановить Kafka, выполнить AI-запрос, показать сохранённое событие, восстановить Kafka и дождаться уведомления.
- Демонстрацию повторной доставки одного `eventId` без нового задания на уведомление.
- Демонстрацию восстановления привязки после сбоя между commit двух сервисов и отказа во внутреннем API при неверном сервисном секрете.

Работа готова, когда оба сервиса независимо запускаются и используют только свои БД, исходный биллинг продолжает работать, событие сохраняется атомарно со списанием, переживает перезапуск приложения и недоступность Kafka, а повторная доставка не создаёт повторных заданий consumer.

На защите объясните, почему нельзя атомарно объединить обычные вызовы PostgreSQL, Kafka и Telegram одной `@Transactional`; когда подтверждаются Kafka send и consumer offset; зачем нужны lease, inbox и стабильный `eventId`; где всё ещё возможно повторное Telegram-сообщение; почему разделены БД и как восстанавливается привязка без общей транзакции двух сервисов.
