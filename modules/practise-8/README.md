# Практика 8. MVC: HTTP-контроллеры сервиса доставки уведомлений

## Цель

Добавить HTTP-интерфейс к сервису из [практики 7](../practise-7/README.md) и разделить ответственность между Model, View и Controller. На семинаре реализуем контроллеры, DTO и обработку ошибок, сохранив существующие правила создания уведомлений, доставки и повторов.

Результат работы: через HTTP можно поставить уведомление в очередь, получить его состояние и запустить обработку. После работы вы должны уметь объяснить, какие решения принимает контроллер, какие — сервис, и почему смена формата ответа не должна менять правила доставки.

## Что уже есть в заготовке

Модуль содержит реализацию задания на основе практики 7. Ниже описаны требования для самостоятельного выполнения; в качестве исходной заготовки используйте код практики 7, а реализацию этого модуля — для разбора и проверки решений.

- `NotificationDraftMapper` проверяет данные черновика, а `NotificationFactoryResolver` выбирает фабрику по каналу `EMAIL`, `PUSH` или `IN_APP`.
- `DeliveryService.enqueue(...)` ставит доставку в очередь; `processDue(now)` выполняет не более одной попытки для каждой готовой доставки за вызов.
- `DeliveryRepository` хранит снимки доставок в памяти и предоставляет `find(id)` и `findAll()`.
- `RetryPolicy` определяет повторы, `DeliveryObserver` получает события попыток, `@TimedExecution` включает профилирование.
- В исходной практике 7 уже подключены Spring Boot и Spring Web MVC. В практике 8 добавлены контроллеры, DTO, сервис приложения, обработчик ошибок и конфигурация Spring. `Main` запускает HTTP-сервер.

## MVC в этой работе

В лекции MVC отделяет обработку действий пользователя от модели и её отображения. Здесь действие пользователя приходит как HTTP-запрос, а интерфейсом служит JSON API на Spring MVC.

- **Model** — состояние уведомлений и доставок вместе с правилами работы с ними. Это не только DTO или запись в базе; сервисы обеспечивают сценарии работы с моделью.
- **Controller** — принимает HTTP-запрос, вызывает сценарий приложения и выбирает HTTP-статус, заголовки и тело ответа.
- **Представление результата** — JSON, построенный из response DTO. DTO описывает публичные поля ответа и не содержит бизнес-поведения.

**Точность терминов Spring:** `@RestController` объединяет `@Controller` и `@ResponseBody`. Его результат записывается в тело ответа через `HttpMessageConverter`; обычные `View` и `ViewResolver` в этом пути не используются. Поэтому DTO не следует называть реализацией `View`. Мы отрабатываем разделение представления и логики на JSON API; для классического серверного MVC с HTML потребовались бы `@Controller`, модель для шаблона и само представление. См. [документацию Spring о `@ResponseBody`](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html).

Путь запроса: HTTP → `DispatcherServlet` → наш контроллер → сервис приложения → модель и хранилище. На обратном пути контроллер преобразует результат в response DTO, а Spring сериализует его в JSON.

### Как это связано с лекцией об архитектурах

- **Слои и их границы.** Контроллер работает через сервис приложения и не обращается к репозиторию. Так правила сценария не приходится повторять в каждом способе доступа: HTTP, консольном интерфейсе или тесте.
- **Use cases из Clean Architecture.** «Создать доставку» — сценарий приложения: проверить данные, выбрать фабрику, создать уведомление и политику, поставить доставку в очередь. Сервис приложения собирает эти шаги; расчёт повторов остаётся в существующем `DeliveryService` и `RetryPolicy`.
- **Направление зависимостей.** HTTP-слой знает о сценариях, а сценарии не знают о контроллерах, `ResponseEntity` и HTTP-кодах. Например, сервис сообщает «доставка не найдена», а обработчик ошибок решает вернуть `404`. Это применение правила зависимостей Clean Architecture на границе HTTP.
- **Ports and Adapters.** Контроллер играет роль входного адаптера. `NotificationSender` уже похож на выходной порт, а `InMemoryNotificationSender` — его адаптер. Но `DeliveryRepository` пока конкретный класс, а в существующих сервисах и мапперах есть инфраструктурные аннотации. Поэтому заготовка не является полной реализацией Clean Architecture.

Смысл этих границ — снизить стоимость изменений: новый формат ответа затрагивает DTO и преобразование, новая политика повторов — модель доставки. Создавать интерфейс для каждого класса или переносить всё приложение в новые слои для этого задания не требуется. Это соответствует тезису лекции «выбрать соразмерную архитектуру».

## Часть 1. Соберите приложение

1. Через `@Configuration` и `@Bean` зарегистрируйте общий `DeliveryRepository`, отправитель `InMemoryNotificationSender` и `DeliveryService`. `DeliveryStatistics` уже является компонентом; если добавляете `DeliveryJournal`, зарегистрируйте его отдельно. Внедрите список `DeliveryObserver`, не создавая повторно уже найденные Spring компоненты.
2. Добавьте singleton-сервис `DeliveryApplicationService` с четырьмя сценариями: создать доставку, найти по UUID, получить список, обработать готовые доставки. Он использует существующие фабрики, мапперы, `DeliveryService` и репозиторий. Конструкторное внедрение делает эти зависимости явными.
3. Внедрите в сервис приложения `Clock.systemUTC()`. Время создания уведомления и момент обработки определяет этот сервис; контроллеру часы не нужны. Для существующего поля `LocalDateTime` используйте `LocalDateTime.ofInstant(clock.instant(), ZoneOffset.UTC)`.
4. Для первого ручного сценария задайте отправителю два результата: `TEMPORARY_FAILURE` с непустой причиной, затем `SUCCESS` с `reason = null`. Создавайте их через `AttemptResultMapper`. Последовательность общая для всех доставок и расходуется по одной записи на фактическую отправку. Перезапуск приложения сбрасывает её и хранилище. Для каждого теста готовьте отдельное состояние.
5. Исходные репозиторий и отправитель не потокобезопасны. Для семинара достаточно одного общего замка вокруг каждого из четырёх сценариев, например `synchronized`-методов одного singleton-сервиса приложения. Все обращения к общему состоянию должны проходить через этот сервис. Синхронизация только в контроллерах или замена `Map` не защищают всю операцию отправки от гонки.

Сервис приложения принимает обычные Java-значения или отдельную команду приложения, возвращает `Delivery`, список доставок или число ошибок наблюдателей. HTTP DTO и `ResponseEntity` остаются в пакете представления. Отсутствие доставки оформите исключением приложения без HTTP-аннотаций. Сервис приложения нужен для сборки сценария и единого доступа к состоянию; правила повторов переносить в него не нужно.

Ориентир для новых классов (точные имена пакетов можно выбрать самостоятельно):

```text
studying.delivery.controller       — два HTTP-контроллера
studying.delivery.dto              — request/response DTO
studying.delivery.mapper           — преобразование Delivery в response DTO
studying.delivery.application      — сценарии приложения
studying.web                       — общий обработчик HTTP-ошибок
studying.config                    — сборка зависимостей
```

Сохраните существующие Factory, RetryPolicy, Observer и профилирование. Контроллер не вызывает `NotificationSender` напрямую. Проверьте запуск Spring-контекста после регистрации зависимостей: обычные unit-тесты с `new DeliveryService(...)` не проверяют работу Spring AOP.

## Часть 2. Реализуйте контроллеры

Нужно реализовать два контроллера с заданными контрактами.

### `DeliveryController`: `/api/deliveries`

| Метод и путь | Действие | Успешный ответ |
| --- | --- | --- |
| `POST /api/deliveries` | Создать уведомление и поставить доставку в очередь | `201 Created`, response DTO и `Location: /api/deliveries/{id}` |
| `GET /api/deliveries/{id}` | Получить текущее состояние доставки | `200 OK`, response DTO |
| `GET /api/deliveries` | Получить все доставки в порядке добавления | `200 OK`, массив DTO; для пустого хранилища `[]` |

Пример тела запроса создания:

```json
{
  "channel": "EMAIL",
  "recipient": "student@example.com",
  "text": "Практика 8",
  "priority": "NORMAL",
  "readyAt": "2026-10-23T12:00:00Z",
  "retry": {
    "maxAttempts": 3,
    "baseDelaySeconds": 10
  }
}
```

Допустимые каналы: `EMAIL`, `PUSH`, `IN_APP`; приоритеты: `LOW`, `NORMAL`, `HIGH`. Все поля, включая объект `retry` и его поля, обязательны и не могут быть `null`. `recipient` и `text` не могут быть пустыми или состоять из пробелов. `maxAttempts` — целое число от 1, включая первую попытку; `baseDelaySeconds` — положительное целое число. Для обязательных чисел в request DTO удобно использовать `Integer` и `Long`, чтобы отличать отсутствие значения от нуля.

Время `readyAt` передаётся в ISO 8601 с часовым поясом и преобразуется в `Instant`. Время создания уведомления задаёт сервер через `Clock`; при преобразовании в существующий `LocalDateTime` используйте UTC. Прошедшее `readyAt` допустимо: такая доставка готова к ближайшему запуску обработки.

В сценарии создания используйте `NotificationDraftMapper.create(...)`, `NotificationFactoryResolver.forChannel(...).create(draft)`, `RetryPolicyMapper.limited(...)` и `DeliveryService.enqueue(...)`. Задержку преобразуйте через `Duration.ofSeconds(...)`. POST только ставит доставку в очередь, без немедленной отправки.

Пример ответа создания (UUID генерируется сервером):

```json
{
  "id": "c7c8a64e-a868-4ed0-bca0-b6a9a00f2d19",
  "channel": "EMAIL",
  "recipient": "student@example.com",
  "text": "Практика 8",
  "priority": "NORMAL",
  "status": "PENDING",
  "attemptsMade": 0,
  "nextAttemptAt": "2026-10-23T12:00:00Z"
}
```

Используйте одинаковую структуру DTO для создания, чтения по идентификатору и элементов списка. После завершения доставки `nextAttemptAt` равен `null`. Не сериализуйте доменный `Delivery` напрямую: публичный контракт не должен зависеть от внутренних типов, в частности `RetryPolicy`.

В `Notification` нет метода `channel()`. В маппере ответа определите канал по конкретному типу: `EmailNotification` → `EMAIL`, `PushNotification` → `PUSH`, `InAppNotification` → `IN_APP` (например, через pattern matching). Не пытайтесь вызвать несуществующий метод и не восстанавливайте канал из строки имени класса.

### `DeliveryProcessingController`: `/api/delivery-processing`

Реализуйте `POST /api/delivery-processing` без тела запроса. Контроллер вызывает сценарий обработки; сервис приложения передаёт `clock.instant()` в `DeliveryService.processDue(...)` и возвращает `200 OK`:

```json
{
  "observerFailuresCount": 0
}
```

Число ошибок берётся из результата `processDue(...)`. Сбой наблюдателя не отменяет завершённую попытку доставки. Не возвращайте клиенту объекты `ObserverFailure`, исключения или ссылки на наблюдателей.

Повторный запрос обрабатывает только доставки, которые снова готовы на текущий момент. Он не должен повторно отправлять `SUCCEEDED` и `FAILED` или отправлять `PENDING` раньше `nextAttemptAt`. Временная или постоянная ошибка отправки — результат бизнес-операции, отражаемый состоянием доставки, а не автоматически HTTP `500`.

Если готовых доставок нет, ответ также `200` с нулём ошибок. Это синхронная учебная команда обработки всей очереди, а не запуск фонового задания. Возвращённое число — количество сбоев наблюдателей, а не количество отправок. При внутреннем исключении ранее обработанные доставки не откатываются: транзакционности всей пачки в этой модели нет.

## Часть 3. DTO, валидация и ошибки

Создайте отдельные request/response DTO и общий обработчик ошибок через `@RestControllerAdvice`.

| Ситуация | HTTP-код |
| --- | --- |
| Некорректный JSON, UUID, enum или дата; пропущенное поле; нарушение правил входных данных | `400 Bad Request` |
| Корректный UUID, для которого нет доставки | `404 Not Found` |
| Непредвиденный внутренний сбой или исчерпание результатов тестового отправителя | `500 Internal Server Error` |

Единый формат ошибки:

```json
{
  "code": "DELIVERY_NOT_FOUND",
  "message": "Доставка не найдена"
}
```

Для ошибок предметной валидации можно использовать существующий `ApplicationErrorCode`; для HTTP-ошибок определите дополнительные коды в слое представления. Не преобразуйте любое `ApplicationException` в `400`: причина может быть внутренней. Клиент не получает stack trace или внутренние детали; техническая причина остаётся в серверном логе.

Проверки формата запроса выполняются на HTTP-границе, бизнес-инварианты — существующими валидаторами. Если используете Bean Validation, подключите необходимую зависимость. Не дублируйте правила доставки в контроллере. При Bean Validation вложенный `retry` требует и проверки наличия, и каскадной проверки (`@Valid`). Ошибки чтения `@RequestBody` и преобразования `@PathVariable UUID` также должны попадать в единый формат ответа.

Для нераспознанного JSON, enum, UUID или даты используйте код `INVALID_REQUEST`, для непредвиденного сбоя — `INTERNAL_ERROR` с нейтральным сообщением. Внутренние нарушения состояния (`INVALID_DELIVERY_STATE`, некорректный результат отправителя и подобные) не относятся к ошибкам клиента. Общий обработчик не должен превращать стандартные ошибки HTTP, например `405` или `415`, в `500`.

## Часть 4. Проверьте поведение

Двигайтесь небольшими шагами: сначала создание и чтение, затем обработка, затем ошибки. После каждого шага проверяйте результат запросом или тестом.

Для проверки контроллеров используйте MockMvc: `@WebMvcTest` с подменой сервиса приложения либо ручную сборку через `MockMvcBuilders`. Полный сценарий проверяйте с реальными сервисом, фабриками и хранилищем в памяти. Если используете `@SpringBootTest` вместе с `@AutoConfigureMockMvc`, отдельный набор дублирующих controller-тестов не обязателен.

В Spring Boot 4 для `@WebMvcTest` и `@AutoConfigureMockMvc` нужен модуль `spring-boot-webmvc-test` (можно подключить `spring-boot-starter-webmvc-test:4.1.1`); одного имеющегося `spring-boot-starter-test` недостаточно для этих аннотаций. Их пакет — `org.springframework.boot.webmvc.test.autoconfigure`. См. [документацию тестирования Spring MVC](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html#testing.spring-boot-applications.spring-mvc-tests).

Проверяемые сценарии:

1. Создание возвращает `201`, `Location`, статус `PENDING` и ноль попыток. Отправитель ещё не вызывался.
2. Чтение созданной доставки и списка возвращает согласованные DTO; пустой список — `[]`.
3. Некорректные входные данные возвращают `400`, неизвестная доставка — `404`, формат ошибок одинаков.
4. Обработка до `readyAt` не вызывает отправитель; ровно в `readyAt` выполняет попытку.
5. Сценарий «временная ошибка → успех» сохраняет расписание повтора и завершает доставку после продвижения тестового времени. Завершённая доставка повторно не отправляется.
6. Сбой наблюдателя отражается в `observerFailuresCount`, состояние доставки при этом сохраняется.
7. Исчерпание результатов отправителя возвращает `500` без раскрытия внутренних деталей.

Ориентир для сценария повторов: при `readyAt = T` и задержке 10 секунд первая обработка в `T` даёт `PENDING`, `attemptsMade = 1`, `nextAttemptAt = T + 10 секунд`; в `T + 9 секунд` ничего не меняется; в `T + 10 секунд` доставка становится `SUCCEEDED`, число попыток равно 2, `nextAttemptAt = null`. Ещё один запуск не вызывает отправитель. Постоянная ошибка или исчерпание лимита попыток должны завершать доставку в `FAILED`.

Используйте управляемый тестовый `Clock`, без `Thread.sleep`. Один неизменяемый `Clock.fixed(...)` подходит для одного момента; для проверки повторов заменяйте его ответ или используйте реализацию с изменяемым временем. Существующие тесты практики 7 должны продолжить проходить.

## Запуск

Нужен JDK 25. Из корня репозитория (команды выполняются отдельно, сервер продолжает работать до остановки):

```bash
./gradlew :modules:practise-8:bootRun
./gradlew :modules:practise-8:test
```

После реализации контроллеров проверьте сценарий вручную:

```bash
curl -i -X POST http://localhost:8080/api/deliveries \
  -H 'Content-Type: application/json' \
  -d '{"channel":"EMAIL","recipient":"student@example.com","text":"Практика 8","priority":"NORMAL","readyAt":"2026-10-23T12:00:00Z","retry":{"maxAttempts":3,"baseDelaySeconds":10}}'

curl -i http://localhost:8080/api/deliveries
curl -i -X POST http://localhost:8080/api/delivery-processing
```

Для чтения одной доставки используйте идентификатор из ответа создания. Дата в примере фиксированная; для демонстрации отложенной доставки задайте будущее время.

После первого запуска обработки ожидайте `PENDING` с одной попыткой. Повторите обработку не раньше чем через 10 секунд и прочитайте доставку по `GET /api/deliveries/{id}`: ожидается `SUCCEEDED` с двумя попытками. Для повторения всей демонстрации перезапустите приложение.

**Работа готова**, когда выполняется эта цепочка, перечисленные проверки проходят, а контроллеры отвечают только за HTTP. На разборе объясните: почему JSON DTO не является доменной моделью; где выбирается `404`; какие классы изменятся при добавлении HTML-представления; что ещё пришлось бы изменить для строгого соблюдения Clean Architecture.

После запуска приложения:

- [Swagger UI](http://localhost:8080/swagger-ui.html) — описание API и выполнение запросов через **Try it out**.
- [OpenAPI YAML](http://localhost:8080/openapi.yaml) — спецификация для Swagger Editor, Postman и других клиентов.
- [Исходный файл спецификации](src/main/resources/static/openapi.yaml) — OpenAPI 3.0.3 с контрактами четырёх операций, схемами DTO, примерами и ошибками.

Swagger UI загружается из CDN и требует интернета. Сам YAML отдаётся приложением и доступен без интернета. Спецификация поддерживается явно: при изменении API обновляйте её вместе с контроллерами и DTO.

Для демонстрации создайте одну доставку через POST, скопируйте `id`, вызовите обработку и прочитайте состояние. Повторите обработку через 10 секунд. Учебный отправитель рассчитан на две фактические отправки; после исчерпания перезапустите приложение.
