# Практика 6. Доставка уведомлений: Strategy и Observer

## Цель

Продолжить сервис уведомлений из [практики 5](../practise-5/README.md): добавить
отправку, повторные попытки и обработку результатов. Применить два поведенческих
паттерна GoF там, где они решают конкретные задачи:

- **Strategy (Стратегия)** — менять правила повторных попыток независимо от отправки.
- **Observer (Наблюдатель)** — подключать независимых потребителей результатов доставки.

Имена компонентов и контракты ниже — ориентиры, а примеры —
псевдокод. Используйте принятые в выбранном языке способы определения контрактов,
передачи зависимостей и представления ошибок. Наследование и DI-контейнер не обязательны.

## Контекст

Интернет-магазин уже умеет создавать email, push и in-app-уведомления.
Теперь их нужно доставлять. Внешний сервис может временно отказать, а некоторые
ошибки, например некорректный адрес, повторной попыткой не исправить.

Для необязательного сообщения, которое быстро теряет актуальность, достаточно
одной попытки. Для уведомления об изменении статуса заказа нужны ограниченные
повторы при временных ошибках. Выбор правила задаётся при создании доставки
и сохраняется на всё время её обработки.

Результаты каждой попытки нужны двум независимым потребителям: журналу
и статистике. Сервис доставки не должен знать, как они хранят и обрабатывают данные.

## Часть 1. Доработка сервиса из практики 5

Сохраните создание уведомлений через Builder и фабрики. Не переносите в них
отправку, повторные попытки или сбор статистики. Ранее написанные тесты должны
продолжать проходить.

Добавьте следующие компоненты:

| Компонент | Ответственность |
|---|---|
| Отправитель | Выполнить одну попытку отправки и вернуть её результат. |
| Доставка | Хранить идентификатор, уведомление, выбранную политику повторов, число выполненных попыток, статус и время следующей попытки, если она назначена. |
| Сервис доставки | Выполнять готовые к отправке доставки, фиксировать результаты, применять политику повторов и оповещать наблюдателей. |
| Хранилище доставок в памяти | Хранить ожидающие и завершённые доставки. |

Уведомление остаётся неизменяемым. Состояние процесса доставки хранится отдельно
от содержания уведомления. Одна доставка сохраняет свой идентификатор при повторах;
каждая новая попытка получает следующий номер, начиная с 1.

Результат отправителя должен различать:

- успех;
- временную ошибку — повтор может помочь;
- постоянную ошибку — повтор не имеет смысла.

Для ошибки сохраняйте код или описание причины. Для статуса доставки достаточно
значений «ожидает», «успешно завершена», «завершена с ошибкой». Отдельные классы
состояний не требуются.

Реальную почту, push-сервис и сеть подключать не нужно. Реализуйте отправитель
в памяти, которому можно задать последовательность результатов, например
«временная ошибка, успех». Он должен записывать полученные уведомления и число
вызовов. Для этой практики достаточно одного такого отправителя для всех каналов:
проверки повторов и наблюдателей от канала не зависят.

## Часть 2. Strategy: правила повторных попыток

Выделите контракт политики повторов:

```text
RetryPolicy.decide(attemptsMade, failure) -> Stop | RetryAfter(delay)
```

`attemptsMade` — число уже выполненных попыток, включая только что завершившуюся.
Политика вызывается только после ошибки. Решение явно означает либо прекращение
доставки, либо назначение новой попытки через положительный интервал времени.

Реализуйте две стратегии:

| Стратегия | Поведение |
|---|---|
| `NoRetryPolicy` | После любой ошибки прекратить доставку. Всего выполняется одна попытка. |
| `LimitedRetryPolicy(maxAttempts, baseDelay)` | Повторять только временные ошибки, пока число выполненных попыток меньше `maxAttempts`. |

Для ограниченных повторов используйте задержку:

```text
delay = baseDelay * attemptsMade
```

Например, при `maxAttempts = 3` и `baseDelay = 10 секунд` после первой временной
ошибки повтор назначается через 10 секунд, после второй — через 20 секунд.
После третьей ошибки доставка завершается. `maxAttempts` включает первую попытку,
а не только повторы. Постоянная ошибка всегда прекращает доставку.

При создании политики проверяйте, что `maxAttempts >= 1`, а `baseDelay > 0`.

Политика не отправляет сообщения, не изменяет доставку, не читает системные часы
и не ждёт через `sleep`. Она только принимает решение. Сервис доставки работает
через общий контракт и не проверяет конкретный тип стратегии. Выбор стратегии
выполняется снаружи и передаётся сервису вместе с новой доставкой.

### Выполнение отложенных попыток

Добавьте операцию обработки с явно переданным временем:

```text
service.processDue(now)
```

Новая доставка ожидает первую попытку; время её готовности задаётся явно при
добавлении. Оно не обязано совпадать со временем создания уведомления.

За один вызов `processDue` каждая готовая доставка обрабатывается не более
одного раза:

1. Если доставка завершена или время следующей попытки позже `now`, пропустить её.
2. Выполнить отправку и увеличить число выполненных попыток.
3. При успехе завершить доставку успешно.
4. При ошибке запросить решение её стратегии. При `Stop` завершить с ошибкой;
   при `RetryAfter(delay)` оставить в ожидании и назначить время `now + delay`.
5. Оповестить наблюдателей о результате выполненной попытки.

При завершении доставки время следующей попытки отсутствует. Время, равное
`now`, уже наступило: такая доставка готова к обработке.

Для проверки времени достаточно последовательно вызывать метод с разными
значениями `now`. Фоновые потоки, таймеры, брокеры сообщений и сохранение очереди
между запусками не требуются. Обработка в рамках задания последовательная.

## Часть 3. Observer: журнал и статистика

После каждой выполненной попытки сервис передаёт наблюдателям неизменяемое
событие `DeliveryAttemptFinished`. Событие содержит:

- идентификатор доставки;
- номер попытки;
- время попытки — переданное в обработку значение `now`;
- результат: успех, временная или постоянная ошибка;
- причину ошибки, если она есть;
- итоговый статус доставки после этой попытки;
- время следующей попытки, если она назначена.

Ошибка попытки и окончательная неудача доставки — разные факты: после временной
ошибки доставка может остаться в ожидании повтора.

Определите общий контракт наблюдателя:

```text
DeliveryObserver.onAttemptFinished(event)
```

Реализуйте двух наблюдателей:

| Наблюдатель | Поведение |
|---|---|
| `DeliveryJournal` | Сохраняет события в памяти, позволяет получить историю попыток по идентификатору доставки. |
| `DeliveryStatistics` | Считает успешные попытки, попытки с временными ошибками и попытки с постоянными ошибками. |

Статистика считает **попытки**, а не доставки. Последовательность «временная
ошибка, успех» увеличивает два разных счётчика по одному разу.

Набор наблюдателей передаётся извне при сборке приложения. Сервис оповещает их
через общий контракт; он не обращается напрямую к журналу или счётчикам и не
проверяет конкретные типы наблюдателей. Достаточно фиксированного списка:
подписка и отписка во время работы не обязательны.

Правила оповещения:

- В рамках обычного выполнения событие передаётся каждому наблюдателю один раз
  на выполненную попытку. Пропущенные и ещё не готовые доставки событий не создают.
- Наблюдатели вызываются синхронно и не должны зависеть от порядка друг друга.
- Ошибка одного наблюдателя не мешает вызову остальных.
- Ошибка наблюдателя не меняет результат отправки, состояние доставки и решение
  о повторе. В частности, сбой статистики после успешной отправки не приводит
  к повторной отправке уведомления.
- Ошибки наблюдателей не теряются: верните их отдельным списком из операции
  обработки либо запишите в отдельный диагностический приёмник. Выбранный способ
  опишите в README решения.

Гарантии доставки событий после аварийного завершения приложения и повторная
доставка событий наблюдателям в это задание не входят.

## Часть 4. Полный сценарий

Соберите компоненты через явную передачу зависимостей. Покажите следующий сценарий:

1. Создать черновик и уведомление средствами практики 5.
2. Добавить доставку с `LimitedRetryPolicy(3, 10 секунд)` и временем готовности `t0`.
3. Подключить журнал и статистику. Задать отправителю результаты «временная ошибка, успех».
4. Вызвать обработку в `t0`: выполнена первая попытка, повтор назначен на `t0 + 10 секунд`.
5. Вызвать обработку в `t0 + 9 секунд`: новых попыток и событий нет.
6. Вызвать обработку в `t0 + 10 секунд`: вторая попытка успешна, доставка завершена.
7. Повторно вызвать обработку с более поздним временем: отправка не повторяется.

В журнале должны быть два события одной доставки с номерами 1 и 2.
В статистике — одна временная ошибка, один успех и ноль постоянных ошибок.

## Тесты

Используйте тестовые средства выбранного языка. Названия сценариев или
отображаемые описания тестов должны быть понятными и написанными по-русски.

Покройте следующие сценарии:

1. `NoRetryPolicy` прекращает доставку после первой ошибки.
2. `LimitedRetryPolicy` назначает правильные задержки при временных ошибках,
   прекращает повторы при достижении лимита и не повторяет постоянные ошибки.
3. `maxAttempts = 1` допускает ровно одну попытку; некорректные параметры
   политики отклоняются.
4. Успешная доставка не повторяется. Завершённая с ошибкой доставка также больше
   не обрабатывается.
5. До назначенного времени отправитель не вызывается; точно в назначенное
   время попытка выполняется.
6. Один и тот же сервис обрабатывает доставки с разными стратегиями согласно
   их правилам. Число попыток и расписание разных доставок независимы.
7. Журнал сохраняет историю, а статистика правильно считает результаты попыток.
8. Оба наблюдателя получают события. Дополнительный тестовый наблюдатель
   подключается без изменения сервиса доставки.
9. Ошибка наблюдателя не мешает остальным, сохраняется в диагностике и не
   вызывает повтор успешной отправки.
10. Полный сценарий из части 4 работает с настоящими Builder, фабрикой, сервисом,
    стратегией, хранилищем и наблюдателями. Внешнюю доставку заменяет отправитель
    в памяти с заданной последовательностью результатов.

Тесты не должны зависеть от системных часов, реального ожидания, сети или порядка
запуска. Все тесты запускаются одной командой выбранного инструмента.

## Что сдавать

- Решение практики 5, дополненное сервисом доставки и хранилищем в памяти.
- Две стратегии повторов и два наблюдателя.
- Отправитель в памяти с управляемыми результатами.
- Unit-тесты и интеграционный тест полного сценария.
- README решения с командой запуска тестов, способом обработки ошибок
  наблюдателей и кратким объяснением ответственности Strategy и Observer.

## Самопроверка

- [ ] Builder и фабрики отвечают за создание уведомлений, а сервис — за доставку.
- [ ] Содержание уведомления отделено от состояния доставки.
- [ ] Стратегия принимает решение о повторе без отправки и ожидания.
- [ ] Сервис не проверяет конкретные типы стратегий и наблюдателей.
- [ ] Лимит попыток включает первую отправку.
- [ ] Наблюдатели получают результаты попыток и не управляют повторами.
- [ ] Сбой наблюдателя не вызывает дублирование успешной отправки.
- [ ] Время передаётся явно, а отложенные попытки проверяются без `sleep`.
- [ ] Тесты практики 5 сохранены, все тесты запускаются одной командой.
